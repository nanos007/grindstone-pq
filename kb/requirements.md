# GRINDSTONE requirements matrix (Agent C, "Mailing-List Ethnographer")

Compiled 2026-10-22 from the bitcoindev archive (gnusha.org public-inbox mbox exports), Delving Bitcoin (Discourse JSON API), the bitcoin/bips repo, and the SHRINCS BIP draft repo.
Source records: `kb/raw/C/sources.yaml`. Factual and timeline claims: `kb/raw/C/claims.yaml`.

**Conventions**
- Quotes are copied verbatim from the archived text. Hard line wraps in emails are joined with one space. `[...]` marks an elision. Markdown emphasis and HTML from the original is shown literally, e.g. `*much*`. Typos are preserved and marked (sic).
- Dates are UTC.
- Priority is our reading of how strongly the community holds a requirement:
  - **must**: stated as a hard constraint by several core contributors, or written into a spec draft.
  - **should**: stated by a credible contributor and not contested.
  - **nice**: a preference, or contested.
- Flags:
  - ⚠ marks something uncertain, a source that is not a mailing-list or Delving post, or a quote taken from a rendered page instead of the raw archive.
  - ↔ marks a requirement that conflicts with another row.

## 6. Observations relevant to GRINDSTONE scope (Agent C notes, not requirements)

1. **The current SHRINCS draft does not grind FORS+C or PORS+FP on its stateless path.** The stateless component is plain FIPS-205 SLH-DSA with custom parameters (d=5, h'=9, a=13, k=10, w=16; 5,777 B). WOTS+C grinding appears only on the stateful path. So FORS+C/PORS+FP grinding (GRINDSTONE E3) is relevant to the competing "optimised SPHINCS+" position (RQ-30, Kudinov–Nick report, SHRIMPS), not to SHRINCS as drafted. We should frame E3 as quantifying what RQ-43 gives up.
2. **The SHRINCS WOTS+C grind layout differs from the plan's §3.5:**
   - `H_grind = sha256(pk_seed ‖ zeros(48) ‖ ADRS[:10] ‖ digest(32 B) ‖ zeros(4) ‖ counter(u16 BE))[:16]`.
   - The first 64-byte block is constant, so the midstate is cacheable and each attempt costs one compression.
   - The counter is 16 bits, not 32. The message is a 32-byte digest, not 16 B.
   - w=16, 32 chains, S=240, so P(success) ≈ 2^−6.
   - Flag for Agent A and the kernel (`cuda/grind_wots_c.cu`): add a "SHRINCS layout" variant.
3. **The SHRINCS stateless path has a second grind.** `PRF_msg_sl` "may be replaced with an XOF [...] from which the caller can sample multiple randomizers for the purposes of grinding to implement hypertree pruning". This is R-grinding, the same per-attempt shape as GRINDSTONE's `grind_fors_c_R` kernel. It is a natural extra measurement target for HW-wallet signing.
4. **"Overgrinding" is already measured on HW wallets (mean only).** UXMSS / SHRINCS-L, w=4, l=64, S_wn=140 vs 96: 3.0–8.0 s → 226–573 s mean signing on Jade Plus, Trezor Safe 3, Ledger Nano gen5/s+ and BitBox02 Nova (Blockstream blog, 2026-08-19). No tail (p99/p99.9) figures were published. This is the closest existing data to GRINDSTONE's RQ2.
